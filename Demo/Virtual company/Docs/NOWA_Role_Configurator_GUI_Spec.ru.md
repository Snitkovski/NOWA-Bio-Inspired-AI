# NOWA Role Configurator — GUI Спецификация

English version: [NOWA_Role_Configurator_GUI_Spec.en.md](NOWA_Role_Configurator_GUI_Spec.en.md)

## Аннотация

Спецификация описывает графический конфигуратор роли как тонкий визуальный слой над уже реализованным `role_config.py`. Собственной валидации интерфейс не вводит: значок годности, ошибки и предупреждения вычисляются вызовами `load_role_config` и `validate_role_config`. Технологическое допущение — Tkinter и разделение вида и контроллера, уже принятые в графике песочницы, вместе с готовой парой языков RU/EN. При смене библиотеки экраны и потоки сохраняются, меняется слой отрисовки. Целевой пользователь правит структурированные данные и классы риска и не редактирует YAML и Python вручную.

Информационная архитектура состоит из списка ролей, мастера из пяти шагов и редактора из шести вкладок: инструменты, словарь решений, эмоциональные реакции, профессиональная интуиция, проверка и тестовый прогон. Список читает каталог `nowa_roles/*/config.yaml` и отдельного реестра не хранит. Обнаружение инструментов предзаполняет риск эвристикой и требует явного подтверждения; до появления живого клиента кнопка работает против `MockMCPClient` либо допускает ручное добавление инструмента. Для чтения тумблер одобрения выключен и недоступен. Для `HIGH_WRITE` и `IRREVERSIBLE` он включён и заблокирован, что повторяет `assert_stage2_invariant` на уровне виджета. Понижение риска ниже эвристики требует непустого текстового обоснования. Вкладка эмоций в этой версии работает в сокращённой паре валентность/возбуждение; расширенный блок осей скрыт до отдельного патча. Затравочные уроки собираются четырёхшаговым мастером и в основном режиме не показывают сырые токены контекста, награду и интенсивность.

Ограничения G1–G7 запрещают собирать `MCPCapability` и `SeedEpisode` в обход парсеров `role_config`, блокируют сохранение, пока `validate_role_config` возбуждает `RoleConfigError`, и не считают предупреждения поводом блокировать запись. Правки живут в памяти до явного сохранения на вкладке проверки; перед первой записью показывается разность, и каждое сохранение создаёт резервную копию предыдущей версии. Тестовый прогон встраивает `BodyLabSession` по текущему несохранённому состоянию роли. Редактор описывает роль как данные и не вводит сущность запущенного сотрудника.

## 0. Технологическое решение

**Tkinter**, консистентно с уже существующей инфраструктурой песочницы
(`nowa_sandbox/gui_app.py`, `gui_controller.py`, `gui_world_tab.py`,
`gui_i18n.py` — включая готовую RU/EN интернационализацию). Это
допущение, не жёсткое требование — если будет принято иное решение,
экраны/потоки ниже переносятся без изменений, меняется только слой
рендеринга.

Новый модуль: `nowa_body/gui_configurator.py` + `gui_configurator_controller.py`
(тот же паттерн разделения view/controller, что в sandbox GUI).

## 1. Информационная архитектура

```
Главный экран (список ролей)
    │
    ├── [Новая роль] → Мастер создания роли (шаги 1–5)
    │
    └── [Открыть роль] → Редактор роли (вкладки)
            ├── Вкладка 1: Инструменты (Tools)
            ├── Вкладка 2: Словарь решений (Action Vocabulary)
            ├── Вкладка 3: Эмоциональные реакции (Affective Mapping)
            ├── Вкладка 4: Профессиональная интуиция (Seed Corpus)
            ├── Вкладка 5: Проверка (Validation & Preview)
            └── Вкладка 6: Тестовый прогон (Dry Run в песочнице)
```

Мастер создания новой роли проводит пользователя через те же пять
вкладок последовательно при первом заполнении; после создания роль
открывается сразу в режиме вкладок (свободная навигация, не мастер).

## 3. Вкладка 1 — Инструменты (Tools)

### Назначение
Обзор и классификация MCP-тулов, доступных роли. Соответствует
`mcp_capabilities` в конфиге.

### Поток "Обнаружить тулы"

```
┌─────────────────────────────────────────────────────────┐
│  Инструменты                          [🔍 Обнаружить тулы] │
├─────────────────────────────────────────────────────────┤
│  Сервер: [1c_erp ▾]                                        │
│                                                             │
│  ┌──────────────────────────────────────────────────┐    │
│  │ ☑ mcp__1c__get_stock_levels                        │    │
│  │   "Get stock levels"                               │    │
│  │   Риск: [READ_ONLY ▾]  Approval: (авто, выкл.)     │    │
│  │   Теги: [procurement ×] [+ тег]                     │    │
│  ├──────────────────────────────────────────────────┤    │
│  │ ☑ mcp__1c__create_purchase_order                   │    │
│  │   "Create purchase order"                           │    │
│  │   Риск: [MEDIUM_WRITE ▾] 💡 предложено эвристикой   │    │
│  │   Approval: ☑ Требуется одобрение (нельзя выключить*)│   │
│  │   Решения: [урочный дозаказ ×][надёжный поставщик ×]│    │
│  │             [дешёвый поставщик ×][диверсификация ×] │    │
│  │             [+ добавить решение]                    │    │
│  │   Теги: [procurement ×]                              │    │
│  ├──────────────────────────────────────────────────┤    │
│  │ ☐ mcp__1c__delete_supplier          🔴 IRREVERSIBLE │    │
│  │   "Delete supplier record"                          │    │
│  │   ⚠ Не включена в роль — тул с необратимым риском   │    │
│  └──────────────────────────────────────────────────┘    │
│                                                             │
│  * HIGH_WRITE/IRREVERSIBLE не могут работать без            │
│    одобрения человека — это архитектурное ограничение       │
│    (assert_stage2_invariant), не настройка.                 │
└─────────────────────────────────────────────────────────┘
```

### Ключевые UX-правила

**"Обнаружить тулы"** вызывает `MCPToolRegistry.register_from_mcp_discovery`
(Фаза 3 — реальный MCP client SDK; до его появления кнопка работает
против `MockMCPClient` с предзаданным набором тулов для демонстрации,
либо позволяет добавить тул вручную кнопкой `[+ Добавить тул вручную]`).

**Риск-класс** — предзаполняется через `classify_risk_heuristic`, но
**никогда не принимается автоматически**. Дропдаун показывает
предложенное значение с пометкой "💡 предложено эвристикой", требуя
явного клика пользователя, чтобы подтвердить или изменить — то же
требование, что уже в докстринге `risk_classifier.py` ("An
administrator MUST confirm... never rely on the heuristic for
HIGH_WRITE / IRREVERSIBLE without human review").

**Тумблер "Approval"** — для READ_ONLY выключен и задизейблен (approval
не имеет смысла). Для HIGH_WRITE/IRREVERSIBLE — **включён и
заблокирован** (нельзя выключить через UI вообще, не просто
предупреждение). Это UI-зеркало `hard_constraints.py::assert_stage2_invariant`
— защита должна быть видна пользователю физически, не только
как ошибка после попытки сохранить.

**Понижение риска ниже эвристики** (например, пользователь меняет
`delete_supplier` с IRREVERSIBLE на LOW_WRITE) — требует
подтверждающего диалога с обязательным текстовым полем "почему это
безопасно понизить":

```
┌─────────────────────────────────────────┐
│  ⚠ Понижение уровня риска                 │
│                                             │
│  Эвристика определила этот тул как         │
│  IRREVERSIBLE. Вы понижаете до LOW_WRITE.  │
│                                             │
│  Почему это безопасно? (обязательно)       │
│  ┌───────────────────────────────────┐   │
│  │                                     │   │
│  └───────────────────────────────────┘   │
│                                             │
│         [Отмена]      [Подтвердить]       │
└─────────────────────────────────────────┘
```

Причина сохраняется в `description` поля capability как аннотация
(`"[risk downgrade justified: <текст>] " + original_description`) —
не отдельное поле в схеме `MCPCapability` (не переусложняем контракт
данных ради UI-аудита), но не теряется.

**"Решения" (`action_types`)** — мультиселект из уже определённого
"Словаря решений" (вкладка 2). Если вкладка 2 ещё пуста — предлагается
переход туда прямой ссылкой в этом же диалоге, не отдельным блокирующим
шагом.

## 4. Вкладка 2 — Словарь решений (Action Vocabulary)

### Назначение

До этой вкладки в предыдущих спецификациях "словарь решений"
(`PROCUREMENT_ACTION_TYPES`) жил только в коде `MotorAdapter`-подкласса
и `ActionSelector`. GUI впервые делает его видимым и редактируемым
пользователем — но **не создаёт заново логику выбора параметров**
(это остаётся кодом `MotorAdapter`, раздел 0 родительской спецификации).
Этот экран определяет только *названия* и *человекочитаемые описания*
решений, которые сотрудник может принимать — состав словаря должен
совпадать с тем, что реализует конкретный `MotorAdapter`-подкласс.

```
┌─────────────────────────────────────────────────────────┐
│  Словарь решений                                           │
├─────────────────────────────────────────────────────────┤
│  Какие решения может принимать этот сотрудник?             │
│                                                             │
│  ┌──────────────────────────────────────────────────┐    │
│  │ urgent_reorder                                      │    │
│  │ "Срочный дозаказ" — заказать у самого быстрого       │    │
│  │  поставщика, не глядя на цену                        │    │
│  │ Используется в тулах: create_purchase_order          │    │
│  ├──────────────────────────────────────────────────┤    │
│  │ diversify_supplier                                   │    │
│  │ "Диверсификация" — заказать у наименее               │    │
│  │  используемого поставщика                             │    │
│  │ Используется в тулах: create_purchase_order          │    │
│  └──────────────────────────────────────────────────┘    │
│                                                             │
│  ⚠ wait_and_monitor всегда доступно неявно —               │
│    не требует тула, означает "ничего не делать"             │
│                                                             │
│  [+ Добавить решение]                                       │
└─────────────────────────────────────────────────────────┘
```

**Важное ограничение UI:** этот экран **не позволяет** создать
`action_type`, для которого не существует ни одного `MotorAdapter`,
умеющего его разрешить в параметры — потому что GUI не пишет код.
Новый `action_type`, добавленный здесь, автоматически помечается как
"⚠ требует реализации в MotorAdapter" до тех пор, пока разработчик не
добавит соответствующий `_select_*`-метод в код роли. Это явная,
видимая граница между тем, что конфигурирует продвинутый пользователь,
и тем, что остаётся задачей разработчика — GUI не пытается скрыть эту
границу, а показывает её честно.

## 5. Вкладка 3 — Эмоциональные реакции (Affective Mapping)

### Назначение
Соответствует `affective_mapping` в конфиге. Ключевой UX-вызов: не
заставлять пользователя вводить сырые числа по осям `AffectiveSpace`
напрямую — большинство пользователей не должны знать, что такое ось
"AXIS_PLACEHOLDER_N" (раздел про полные оси — патч v1.1, следующий
этап после этой спецификации).

```
┌─────────────────────────────────────────────────────────┐
│  Эмоциональные реакции                                      │
├─────────────────────────────────────────────────────────┤
│  Что происходит?  [stock_critical_low            ▾ ]      │
│  [+ Новое событие]                                          │
│                                                             │
│  Насколько это плохо или хорошо?                            │
│  Очень плохо  ●───────○───────○  Очень хорошо              │
│               (−0.7)                                        │
│                                                             │
│  Насколько это тревожно или спокойно?                       │
│  Спокойно  ○───────○───────●  Тревожно                     │
│                            (0.8)                             │
│                                                             │
│  ┌─ Пресеты ────────────────────────────────────┐         │
│  │ [🔥 Кризис] [✓ Успех] [💔 Разрыв доверия] [😐 Рутина] │  │
│  └────────────────────────────────────────────────┘         │
│                                                             │
│  Теги: [procurement ×] [urgency ×] [risk ×] [+ тег]         │
│                                                             │
│  ▸ Продвинутая настройка (отдельные оси AffectiveSpace)     │
│                                                             │
└─────────────────────────────────────────────────────────┘
```

### Ключевые UX-правила

**Два слайдера = valence/arousal**, ровно то, что уже поддерживает
`_parse_affective_mapping` (shorthand-форма). Значения слайдера
записываются напрямую в `valence`/`arousal` поля YAML.

**Пресеты** — не отдельная сущность в схеме, а просто предзаполнение
слайдеров разумными значениями ("Кризис" → valence=-0.8, arousal=0.7;
"Рутина" → valence=0.0, arousal=0.1 и т.д.), которые пользователь может
затем подвинуть. Чистый UX-сахар поверх той же shorthand-схемы.

**"Продвинутая настройка"** — свёрнутый по умолчанию блок (progressive
disclosure), раскрывающий явный ввод по отдельным осям
`AffectiveSpace` — это UI-эквивалент `explicit axes:` формы из патча
v1.1. **Этот блок не активен до тех пор, пока патч v1.1 не закрыт** —
до этого момента вкладка 3 работает только в shorthand-режиме, кнопка
"Продвинутая настройка" скрыта целиком, не показана заблокированной.
Не показывать пользователю функциональность, которой ещё физически нет
за ней.

**Автоматические подсказки событий** — при переключении на вкладку 3
после того, как на вкладке 1 определены тулы, GUI может предложить
типовые события на основе `event_classifier` роли (если он уже
реализован в коде — статический анализ невозможен для произвольной
функции, поэтому подсказка работает только через заранее
задекларированный список "часто классифицируемых событий" внутри
`event_classifier.py`, опциональный атрибут `KNOWN_EVENT_NAMES: List[str]`).
Это не обязательная часть Definition of Done этой спецификации —
удобство, не требование.

## 6. Вкладка 4 — Профессиональная интуиция (Seed Corpus)

### Назначение — самая сложная UX-задача этой спецификации

Пользователь не должен видеть `context_tokens`, `EventType.ACTION`,
сырые числа reward/intensity. Задача — превратить "урок" в
повествовательную форму: **"Когда происходит X → правильно делать Y →
потому что Z"**.

### Мастер "Научить решению"

```
┌─────────────────────────────────────────────────────────┐
│  Новый урок                                    Шаг 1 из 4  │
├─────────────────────────────────────────────────────────┤
│  Когда это происходит...                                    │
│                                                             │
│  ☑ Критически низкий остаток на складе                     │
│  ☐ Поставщик подвёл (дефолт)                                │
│  ☐ Бюджет почти исчерпан                                    │
│  ☐ Заказ пришёл вовремя                                     │
│                                                             │
│  (список = события из вкладки 3 "Эмоциональные реакции")   │
│                                                             │
│                                    [Отмена]   [Далее →]     │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│  Новый урок                                    Шаг 2 из 4  │
├─────────────────────────────────────────────────────────┤
│  ...правильное решение —                                    │
│                                                             │
│  ○ Срочный дозаказ (urgent_reorder)                         │
│  ○ Заказ у надёжного поставщика                             │
│  ○ Заказ у дешёвого поставщика                               │
│  ○ Диверсификация поставщиков                                │
│  ○ Ничего не делать, просто наблюдать                        │
│                                                             │

│                                                             │
│  ┌─ Предпросмотр ────────────────────────────────────┐    │
│  │ Когда критически низкий остаток на складе —          │    │
│  │ правильно сделать срочный дозаказ,                    │    │
│  │ потому что это восстанавливает остаток.                │    │
│  │ Важность: высокая. Запомнить крепко: да.               │    │
│  └────────────────────────────────────────────────────┘    │
│                                                             │
│                        [← Назад]   [Сохранить урок]          │
└─────────────────────────────────────────────────────────┘
```

### Маппинг мастера на `SeedEpisode`

| Экран мастера | Поле `SeedEpisode` |
|---|---|
| Шаг 1 (события) | `context_tokens` — каждое выбранное событие разворачивается в его токены через уже существующий `_event_to_tokens`-подобный маппинг (событие → `["event:X", "valence:...", "arousal:...", "domain:..."]`) |
| Шаг 2 (решение) | `action` |
| Шаг 3 (результат) | `consequence` |
| Шаг 4, слайдер важности | `reward`/`intensity` (слайдер 0–10 линейно маппится на 0.0–1.0 для обоих; можно развести на два слайдера позже, если понадобится независимый контроль) |
| Шаг 4, чекбокс | `reinforce` |

**Список "уже существующих уроков"** на вкладке 4 показывает все
`SeedEpisode` в той же повествовательной форме, что предпросмотр шага
4 — не сырые dict/YAML. Редактирование существующего урока открывает
тот же 4-шаговый мастер, предзаполненный текущими значениями.

**Совместимость с `seed_corpus_module`:** если конфиг роли использует
`seed_corpus_module` (как сейчас procurement, раздел 4.2 родительской
спецификации), вкладка 4 показывает корпус в режиме **только для
чтения**, с плашкой:

```
ℹ Этот словарь интуиции определён в коде (seed_corpus.py),
  не в этом конфиге. Чтобы редактировать через интерфейс,
  сначала перенесите его в inline-формат — [Перенести в конфиг →]
```

Кнопка "Перенести в конфиг" — однократное действие, переписывающее
`config.yaml` так, что `seed_corpus_module` заменяется на `seed_corpus:`
с теми же данными инлайн (используя уже существующий Python-список как
источник, без потери ни одного урока) — после этого редактирование
через мастер становится доступно.

## 7. Вкладка 5 — Проверка (Validation & Preview)

### Назначение
Живой вызов `validate_role_config` при каждом изменении на любой
вкладке — не отдельная кнопка "Проверить", а постоянный статус-бар
внизу окна плюс детальный отчёт на этой вкладке.

```
┌─────────────────────────────────────────────────────────┐
│  Проверка конфигурации                                      │
├─────────────────────────────────────────────────────────┤
│  ✗ Найдены проблемы, требующие исправления:                │
│                                                             │
│  ┌──────────────────────────────────────────────────┐    │
│  │ ✗ Урок "срочный дозаказ" ссылается на решение       │    │
│  │   "экстренная эскалация", которого нет ни в одном    │    │
│  │   инструменте. Этот урок никогда не сработает.        │    │
│  │   → [Перейти к уроку]  [Перейти к словарю решений]   │    │
│  └──────────────────────────────────────────────────┘    │
│                                                             │
│  ⚠ Предупреждения (не блокируют сохранение):                │
│                                                             │
│  ┌──────────────────────────────────────────────────┐    │
│  │ ⚠ Решение "диверсификация поставщиков" не имеет     │    │
│  │   ни одного урока — сотрудник начнёт без опыта        │    │
│  │   по этому решению.                                    │    │
│  │   → [Научить решению]                                 │    │
│  └──────────────────────────────────────────────────┘    │
│                                                             │
│  ✓ Проверено: 4 инструмента, 4 решения, 8 уроков            │
│                                                             │
│                              [Сохранить]  (заблокировано*)  │
│  * пока не исправлены ✗-ошибки                               │
└─────────────────────────────────────────────────────────┘
```

**Прямое отображение исключений/warnings** из `role_config.py`:
`RoleConfigError` → красная карточка с блокировкой сохранения;
`warnings.warn(...)` (unseeded action_types) → жёлтая карточка, не
блокирует. Текст ошибки **переформулируется** на язык предметной
области ("решение", "урок", "инструмент"), не показывается как сырое
Python-исключение — но по клику "Показать техническую деталь"
доступен оригинальный текст `RoleConfigError` для разработчика,
если понадобится отладка.

**Кнопка "Сохранить"** — единственное место, где GUI пишет в
`config.yaml`. Перед записью — diff-превью (раздел 9).

## 8. Вкладка 6 — Тестовый прогон (Dry Run)

### Назначение
Переиспользует уже написанный `BodyLabSession` — GUI не создаёт новую
тестовую инфраструктуру, вкладка 6 буквально встраивает
sandbox/body lab в редактор роли.

```
┌─────────────────────────────────────────────────────────┐
│  Тестовый прогон                                             │
├─────────────────────────────────────────────────────────┤
│  Сценарий: [Критический дефицит на складе  ▾]               │
│  [▶ Прогнать 20 тактов]                                      │
│                                                             │
│  Тик 14: действие = urgent_reorder                          │
│    → Мотор: supplier_002, sku_a, qty=45.0                    │
│    → place_order: accepted (стоимость=360.00)                │
│    → эмоциональный отклик: доверие +0.3, тревога −0.2         │
│                                                             │
│  Тик 15: действие = wait_and_monitor                        │
│                                                             │
│  [Показать полный лог]  [Показать содержимое памяти]         │
│                                                             │
│  📊 За 20 тактов: 3 заказа, 0 отклонено, накоплено 3 урока   │
└─────────────────────────────────────────────────────────┘
```

**Реализация:** конструирует `BodyLabSession` с текущим
(несохранённым) состоянием конфига в памяти — не требует записи в
`config.yaml` перед тестированием. Использует `MockMCPClient`
сценарии, уже определённые в `lab_session.py` (`SCENARIO_QUIET`,
`SCENARIO_STOCK_CRITICAL`, `SCENARIO_SUPPLIER_DEFAULTED`). Это даёт
пользователю возможность "погонять то, что есть" (как было
сформулировано в постановке задачи) прямо из процесса редактирования,
до сохранения и тем более до реального MCP-подключения.

## 9. Сохранение — diff-превью

Учитывая, сколько итераций правок конфигурации вероятно потребуется
(по аналогии с тем, сколько патчей потребовала сама песочница) —
сохранение должно показывать явный diff перед записью:

```
┌─────────────────────────────────────────────────────────┐
│  Сохранить изменения?                                        │
├─────────────────────────────────────────────────────────┤
│  + добавлен инструмент: mcp__1c__cancel_order                │
│  ~ изменено: create_purchase_order, риск LOW_WRITE → MEDIUM │
│  + добавлен урок: "при дефолте поставщика — диверсификация"  │
│                                                             │
│              [Отмена]        [Сохранить]                    │
└─────────────────────────────────────────────────────────┘
```

**Версионирование:** каждое сохранение копирует предыдущую версию
`config.yaml` в `nowa_roles/procurement/.history/config_<timestamp>.yaml`
перед перезаписью — простой файловый backup, не требует git-интеграции
для первой версии. Кнопка "История изменений" на главном экране роли
показывает список версий с возможностью просмотра diff и отката.

## 10. Ограничения (обязательны к соблюдению)

| # | Ограничение |
|---|---|
| **G1** | GUI никогда не вызывает `MCPCapability`/`SeedEpisode` конструкторы напрямую в обход `role_config.py` — все объекты строятся через `load_role_config`/парсеры того же модуля, чтобы не расходиться в валидации |
| **G2** | Тумблер approval для HIGH_WRITE/IRREVERSIBLE физически заблокирован в UI (disabled widget), не просто visually discouraged — зеркалит `assert_stage2_invariant` на уровне интерфейса |
| **G3** | Кнопка "Сохранить" недоступна, пока `validate_role_config` бросает `RoleConfigError` — warnings не блокируют |
| **G4** | Понижение риска ниже эвристики требует непустого текстового обоснования — форма не принимает пустую строку |
| **G5** | Вкладка 4 (Seed Corpus) никогда не показывает пользователю сырые `context_tokens`/`reward`/`intensity` в основном режиме — только в опциональном "техническом" виде по явному запросу |
| **G6** | Изменения на любой вкладке не пишутся в файл до явного нажатия "Сохранить" на вкладке 5 — редактор работает с in-memory `RoleConfig`, diff показывается перед первой записью |
| **G7** | Каждое сохранение создаёт backup предыдущей версии перед перезаписью |

## 12. Открытые вопросы

**Q-GUI-1: реальное MCP tool discovery.** Кнопка "Обнаружить тулы"
(раздел 3) зависит от `register_from_mcp_discovery`, которая в Фазе 1
оставлена как `NotImplementedError` до появления конкретного MCP client
SDK (Фаза 3). До этого момента кнопка работает только против
`MockMCPClient` с демонстрационным набором — открытый вопрос, насколько
это ограничение приемлемо для первой версии GUI, или нужно параллельно
ускорить Фазу 3 хотя бы для чтения tool schema (не для реального
исполнения).

**Q-GUI-2: миграция `seed_corpus_module → inline` — атомарность.**
Кнопка "Перенести в конфиг" (раздел 6) переписывает файл. Нужно решить,
должна ли она также предлагать удалить исходный Python-модуль
(`seed_corpus.py`) или оставлять его как мёртвый код для истории —
рекомендация: оставлять, не удалять автоматически, GUI не должен
трогать файлы вне `config.yaml` и `.history/`.

**Q-GUI-3: локализация.** `gui_i18n.py` в песочнице уже поддерживает
RU/EN. Нужно решить, использовать ли ту же инфраструктуру для нового
конфигуратора (рекомендуется, для консистентности) или это отдельный
i18n-слой.
